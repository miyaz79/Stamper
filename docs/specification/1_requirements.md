# 要件定義書：Stamper

## 1. プロジェクト概要
### 1.1. 背景と課題
* 現在、勤怠管理はスプレッドシートで、経費申請はBacklog + Excelで個々に管理されており、非効率な状態にある
* チームリーダーは週次・月次でのチームメンバーの作業時間集計に多くの時間を費やしている
* スプレッドシート管理では入力ミスが発生しやすく、集計作業も手間がかかっている
* リモートワーク環境下でも効率的に勤怠・経費を管理できるシステムが必要とされている

### 1.2. プロジェクトの目的とゴール
* **目的**: スプレッドシートによる手動での記録・管理をなくし、どこからでも簡単かつ正確に勤務時間と経費を記録・確認できるWebアプリケーションを作成する
* **ゴール**:
  * 2週間でPoCとして勤怠管理機能の基本部分を実装し、フィードバックを取得する（Specific, Time-bound）
  * チームリーダーの勤怠集計作業時間を現状から75%削減する（Measurable）
  * 全従業員が直感的に操作できるUIを実現し、マニュアルなしで利用可能な状態にする（Achievable）
  * 勤怠入力の正確性を向上させ、集計ミスをゼロにする（Relevant）

## 2. スコープ
### 2.1. 対象範囲 (Scope In)
* 勤怠管理機能（ダッシュボード、日次入力、月次一括編集、勤務表表示）
* 経費申請機能（領収書アップロード、AI-OCRによる自動解析）
* 管理機能（チームメンバーの作業時間集計確認）
* ユーザー認証（Amazon Cognito）

### 2.2. 対象外範囲 (Scope Out)
* 他システムとの連携（人事システム、会計システムなど）
* 承認ワークフローの完全実装（PoCでは機能の基礎部分のみ）
* 過去データの移行
* 法的要件やコンプライアンス対応（労働基準法準拠など）

## 3. ユーザーロール
* **一般ユーザー（申請者）**: 自身の勤務時間を記録・閲覧し、経費を申請する役割
* **管理者（承認者）**: 一般ユーザーの勤怠・経費データを承認する役割、およびチームメンバーの作業時間集計データを確認する役割

## 4. 機能要件
| ID | 機能名 | 概要 (ユーザーストーリー) | 優先度 (MoSCoW) |
|---|---|---|---|
| F-001 | ユーザー認証 | 一般ユーザーとして、個人のアカウント（Amazon Cognito）でシステムにログインしたい。それは自分のデータのみにアクセスするためだ。 | Must |
| F-002 | ダッシュボード表示 | 一般ユーザーとして、月次の作業サマリー（作業項目ごとの合計時間、残業時間、休暇取得状況）と週次（月曜〜日曜）の合計作業時間を確認したい。それは自分の勤務状況を一目で把握するためだ。 | Must |
| F-003 | 日次勤怠記録 | 一般ユーザーとして、カレンダーから日付を選択して日々の勤怠を記録したい。それは正確な勤務記録をその日のうちに残すためだ。 | Must |
| F-004 | 作業項目入力 | 一般ユーザーとして、「大（所属部署）」「中（プロジェクト名）」「小（案件名）」の3階層で作業項目を選択し、時間を入力したい。それは作業内容を適切に分類して記録するためだ。 | Must |
| F-005 | 休暇登録 | 一般ユーザーとして、「全休（7.5時間）」または「時間休」を選択して記録したい。それは休暇取得を勤務記録に正確に反映させるためだ。 | Must |
| F-006 | 勤務時間自動計算 | 一般ユーザーとして、入力した作業時間から始業・終業時刻、休憩時間が自動計算されるようにしたい。それは計算ミスを防ぎ、入力の手間を省くためだ。 | Must |
| F-007 | 月次一括編集 | 一般ユーザーとして、月間の勤怠データをテーブル形式で一覧し、まとめて編集・保存したい。それは過去のデータをまとめて効率的に修正するためだ。 | Should |
| F-008 | 勤務表表示 | 一般ユーザーとして、自動計算された始業・終業時刻を含む月間勤怠データをテーブル形式で確認したい。それは月次の勤務状況を俯瞰するためだ。 | Must |
| F-009 | 領収書アップロード | 一般ユーザーとして、領収書の画像ファイル（PNG, JPGなど）をアップロードしたい。それは経費申請のためのエビデンスを残すためだ。 | Should |
| F-010 | AI-OCR自動解析 | 一般ユーザーとして、アップロードした領収書から「日付」「支払先」「インボイス番号」「適用」「金額」をAI (AWS Textract) が自動で抽出してほしい。それは手入力の手間を省き、正確なデータを素早く得るためだ。 | Should |
| F-011 | 申請・承認ワークフロー（勤怠） | 一般ユーザーとして、記録した月間勤怠を上長に申請し、上長が承認・差し戻しできるようにしたい。それは正式な勤怠記録として承認を得るためだ。 | Could |
| F-012 | 申請・承認ワークフロー（経費） | 一般ユーザーとして、解析された領収書データに基づき、経費として正式に申請し、承認を得たい。それは経費精算プロセスを効率化するためだ。 | Could |
| F-013 | レポート出力 | 一般ユーザーとして、勤怠データや経費データをPDFやCSVファイルとしてダウンロードしたい。それは外部システムへの入力や書類提出に利用するためだ。 | Could |
| F-014 | 作業時間集計確認 | 管理者として、チームメンバーの作業項目ごとの作業時間の集計データを確認したい。それは部門やプロジェクト単位でのリソース配分の把握や工数管理のためだ。 | Must |
| F-015 | 作業項目の管理機能 | 管理者として、作業項目の大・中・小分類を設定・管理したい。それはチーム全体で一貫した作業分類を使用するためだ。 | Could |
| F-016 | 打刻機能 | 一般ユーザーとして、「出勤」「退勤」ボタンを押した時刻を記録したい。それは正確な勤務開始・終了時間を記録するためだ。 | Won't |
| F-017 | リマインダー機能 | 一般ユーザーとして、月末に入力漏れがある場合に通知を受け取りたい。それは勤怠記録の抜け漏れを防ぐためだ。 | Won't |

## 5. 非機能要件
| ID | 種別 | 具体的な要件内容 |
|---|---|---|
| NF-001 | パフォーマンス | ページ読み込みやデータ処理のレスポンス時間は3秒以内を目標とする |
| NF-002 | セキュリティ | PoCではAmazon Cognitoによる認証を実装し、将来的にはGoogleWorkspace認証とSSOを実現する |
| NF-003 | ユーザビリティ | 操作が直感的で分かりやすく、マニュアルなしで使えるUIを実現する |
| NF-004 | レスポンシブ対応 | PCだけでなく、スマートフォンやタブレットでも快適に操作できるレスポンシブデザインを採用する |
| NF-005 | 可用性 | PoCでは問わないが、将来的には業務時間内（平日9:00-19:00）の可用性99.5%以上を目指す |
| NF-006 | データ保持 | 勤怠データは5年間、経費データは7年間の保存を可能にする |

## 6. その他
### 6.1. 制約条件
* **期間**: 勤怠管理機能のPoCを2週間で実現し、フィードバックを得る
* **予算**: PoCフェーズではクラウドリソース使用量の最適化を図る
* **技術**: アーキテクチャ設計書に記載されている技術スタックに準拠する

### 6.2. 用語定義
* **PoC (Proof of Concept)**: 概念実証。本プロジェクトでは勤怠管理機能を優先的に開発し、実用性を検証する段階
* **SSO (Single Sign-On)**: シングルサインオン。一度の認証で複数のシステムにアクセスできる仕組み
* **全休**: 1日単位の休暇（7.5時間として計算）
* **時間休**: 時間単位の休暇
